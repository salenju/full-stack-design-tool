## 四、三个已确认的缺陷（不是"没做"，是"做错了"）

1. **视觉导入端到端发不出图片**
   `apps/cli/src/commands/import.ts:119` 读了文件并算出 base64，但没有传给 extractor（`:120-124` 只传 `imagePath`）；
   `packages/importer/src/vision.ts:270` 又把 `input.imagePath` 直接当 `imageBase64` 塞给 `callModel`。
   结果是发给模型的是**路径字符串**，不是图片数据。`fsdt import image` 实际不可用。

2. **`settings.backend.swagger = false` 时生成的后端编译不过**
   `packages/generators/nestjs/src/module.ts:151` 按开关省略 `@nestjs/swagger` 依赖，
   但 `controller.ts:147-149`、`dto.ts:213`、`response.ts:102` 无条件 `import ... from '@nestjs/swagger'`。
   依赖被删了、import 还在 → tsc 报错。

3. **`fsdt gen` 不跑任何门禁**
   `gen.ts` 全文没有 `runLint` / `validateIR` / `assertValidIR`。
   只有在 `saveIR` 写盘时才校验，所以手工编辑出一个语义非法的 `design/ir.json`，`gen` 照样生成产物。

## 六、按"能不能上手用"排的优先级

1. **`apps/web`** —— 没有它，整个产品的交互价值为零，用户必须手写 JSON 才能建模。
2. **往返（区块标记 + 三方合并）** —— 没有它，重新生成会覆盖手写代码，AI 生成的代码留不住。
3. **`gen` 门禁 + Lint 修复执行器** —— 现在错误能一路传到生成物。
4. **`apps/server` + 服务模式** —— 快照、项目列表、多画布都挂在它上面。
5. **AI 填充** —— 依赖 1 和 4 的入口。

## 七、本次审计过程中被验证出来的既有缺陷

以下四条不是"读代码推测"，是实际跑起来撞到的。

### 1. `fsdt gen` 不跑门禁，非法 IR 能一路生成

`scripts/demo/ir.json` 从建起来那天就违反 **IR002（字段 ID 全局唯一）**——API 的 query / body / response 字段复用了表字段的 ID，共 18 处重复。
`fsdt lint` 报 0 问题、`fsdt gen` 照常出 31 个文件，**只有 `saveIR` 会拦**。所以这份非法数据在 CLI 时代一直没被发现，直到工作台第一次启动写盘才炸出来。
已修数据（给 API 字段分配独立 ID），但"gen 不跑门禁"这个洞还在。

### 2. `L005` 与 UI Schema 的字段索引不一致，正确绑定被判成缺失

- `L005` 要求页面的 `form.bindings[].fieldRef` 命中**请求体字段的 ID**；
- `emitUiSchema` 建 `fieldById` 时**只索引表字段**（`emit-ui-schema.ts:738-741`）。

结果是"绑表字段"这种唯一能生成出控件的写法，必然触发 L005 警告；改绑请求体字段则 Lint 干净但表单渲染不出任何输入框。两者不可兼得。
已修：L005 增加按字段名兜底（与 L014 的 `findFieldIdByName` 同策略），52 个 lint 测试仍全绿。

### 3. `core-ir` 的 Node 依赖会毒化浏览器构建

`io.ts` 静态 `import ... from 'node:fs/promises'`、`hash.ts` 静态 `import ... from 'node:crypto'`。只要前端 import 了 `@fsdt/core-ir` 的任何值（比如 `createTableNode`），这俩模块就会被求值，vite 直接抛
`Module "node:fs/promises" has been externalized for browser compatibility` —— **整个应用白屏**。
已修：`io.ts` 的三个文件函数改成函数内动态 import；`node:crypto` 由 apps/web 的 vite 插件给一个"能加载、一调用就报错"的壳。core-ir 的 218 个测试全绿。

### 4. pnpm isolated 布局装不上 vite 8 的 plugin-vue

`ERR_PNPM_CODEBUDDY_BROKER_DENY  ENOENT: ... symlink '../../../@rolldown+pluginutils@1.0.1/...'`，加不加沙箱都一样。
已在仓库根加 `.npmrc` 固定 `node-linker=hoisted`，代价是丢掉幽灵依赖检测。

## 八、2026-10-23 增补：已补齐的缺口

逐条修掉上一节列出的「半成品」，测试从 669 增至 701。

### 1. Lint 自动修复器（原来只有类型定义）

新增 `packages/lint/src/fixes.ts`：

- `applyFixes(ir, issues)` 支持已有的 7 种 `LintFix`；返回新 IR，不改入参。
- 无法推断的（枚举取值）**跳过并说明原因**，不塞假值——猜一组值比不修更糟，用户会以为工具懂业务语义。
- 载荷与前提不符时跳过（例如字段已被改名），不硬改。

接到三处：

| 入口 | 用法 |
|---|---|
| CLI | `fsdt lint --fix`，修完写回 IR 并重跑一遍 |
| 工作台 | Lint 面板「一键修复 N 项」按钮，修完整体替换进 store（可撤销） |
| 库 | `applyFixes` 直接调用 |

实际验证：造一份「字段名 `Device_Name` + 列表接口缺分页」的 IR，`--fix` 后字段变 `deviceName`、query 补出 `page/pageSize`，L005 的 `bindField` 也一并修掉。

### 2. `gen` 的门禁（原来是完全裸奔）

`coerceToIR` 只跑 Zod 结构校验（IR000），**不跑语义校验**——所以一份 18 处字段 ID 重复的 IR 能一路生成出 31 个文件。

现在 `fsdt gen` 渲染前先跑 `runLint(ir, { includeIRDiagnostics: true })`，有 error 级问题就中止并列出诊断，`--skip-verify` 才放行。只拦 error 不拦 warn：存量 warn 清不完的项目会被永久卡住，用户只能天天加 `--skip-verify`，门禁等于不存在。

### 3. `lint` 现在能看到 IR00x

原来 `fsdt lint` 只跑 L00x，导致「gen 拦住了、lint 说 0 问题」这种自相矛盾的体验。`runLint` 增加 `includeIRDiagnostics` 选项，CLI 与工作台都打开它。

### 4. Vue 生成器：容器与七个属性

| 原缺口 | 现状 |
|---|---|
| `tabs` / `card` 只有 TODO 注释 | 按 `componentIds` 嵌套渲染；顶层跳过被引用的组件（否则同一组件出两份）；悬空引用留注释 |
| `visibleWhen` | 生成外层 `<template v-if>`（整体显隐，不是逐个控件） |
| `confirm` | `ElMessageBox.confirm` 在调接口**之前**，并自动 import |
| 列 `formatter` | 走作用域插槽 `{{ 表达式 }}`，不是 `el-table-column` 的 formatter prop |
| `form.loadApi` | 生成 `loadForm(id)` 回显函数 |
| `table.rowKey` | `row-key="xxx"` |
| `form.mode` | 参与回显与提交路径 |
| `readOnly` 字段 | 渲染成 `disabled`（编辑页要看得见）而不是删掉；UI Schema 新增 `readOnly` 字段透出 |

### 5. NestJS 生成器

- **修掉 `swagger=false` 编译不过**：`package.json` 按开关去掉 `@nestjs/swagger`，但 controller / dto / response 仍无条件 import。现在三处渲染函数都接收 `swagger` 开关；关闭时装饰器与 import 一起消失，Update DTO 需要的 `PartialType` 改从 `@nestjs/mapped-types` 来。
- **补 `src/common/`**：`pagination.dto.ts`（page/pageSize，带 `@Type(() => Number)`）、`http-exception.filter.ts`（统一 `{ statusCode, message, method, path, timestamp }`，5xx 才打堆栈）、`response.interceptor.ts`（`{ code, message, data }`）。响应包装**只生成不注册**——包一层之后响应体就不再等于 OpenAPI 的 schema，得由用户自己决定。
- **补 `SwaggerModule` 装配**：`main.ts` 里 `DocumentBuilder` + `SwaggerModule.setup('docs', ...)`，受 `settings.backend.swagger` 控制。
- **不支持的值显式报错**：`backend.orm !== 'prisma'`、`frontend.ui !== 'element-plus'` 时直接抛错，不再静默生成 Prisma / Element Plus 代码。

## 九、2026-10-23 增补二：sample 的三种可直接用的导出

`seed.json` 只是数据，用户还得自己拼请求、自己写 INSERT；而这三类文件的拼装规则是死的，手写一遍每个人都会写错一次。

新增 `packages/sample/src/exports.ts`，`fsdt sample --format` 支持四种（可重复）：

| 格式 | 产物 | 说明 |
|---|---|---|
| `json`（默认） | 每表一个 JSON + `index.ts` | 原有行为，给 MSW / mock 服务器 |
| `http` | `api-samples.http` | REST Client 能直接点；带 method、完整 URL、查询串与 JSON body |
| `postman` | `postman-collection.json` | v2.1，能直接 import；服务地址走 collection 变量，不硬编码进每条请求 |
| `sql` | `seed.sql` | 可直接执行；单引号转义成两个，null 写 `NULL` 而不是 `''` |

实现上的几个判断：

- **取值来源**：请求体字段优先用 `field.example`，其次去「任意一张表里同名字段」找示例值。不按「本接口响应字段反查表」找——创建类接口的响应字段常常叫 `deviceId` 而请求体叫 `name`，两边对不上就只剩 TODO。
- **路径参数**：`{id}` 会尽力替换成示例值，替换不了就保留占位。留占位比塞假值好——假值会被当成真的跑过去。
- **SQL 分批**：默认 100 行一条 INSERT，避免单条语句过长。
- **确定性**：同一 seed 两次生成逐字节一致（有测试守着）。

`--format` 多值时必须配合 `--out`：终端里把 JSON 和 SQL 混着打印出来没法用。

## 十、一条审计更正

上一版把「`ref` 字段没生成 `$ref`」记成缺口。复核 `field-schema.ts:86-92` 的注释后确认这是**刻意决策**：

> 外键在 JSON 里就是目标表的主键值；用 `$ref` 指向整表会生成错误类型，所以这里取目标表的主键类型（string），并标注 `x-dsg-fk` 供生成器写关系。

这个判断是对的——`{ $ref: '#/components/schemas/Device' }` 会让客户端以为要传 `{ id, name, status, ... }` 整个对象，而实际只传 `deviceId` 字符串。若真要表达「这是某表的主键」，OpenAPI 3.1 没有现成机制，用 `x-dsg-fk` 扩展比篡改类型诚实。

所以 OpenAPI 侧真正的缺口只剩 `x-dsg-mappings`（把 `map` 边的字段映射写进契约）。价值不高：前端消费的是 UI Schema，不是 OpenAPI；写进契约主要是给第三方工具看。

## 十一、2026-10-23 增补三：往返机制 + CI

上一节把「往返机制」列在仍未完成里，它其实是**优先级第二**的缺口（第一是工作台，已补）：
没有它，用户改过一次生成代码就再也不敢跑 `gen`，工具价值在第一次手工修改后归零。

### 1. 区块级三方合并（新增 `packages/generators/runtime/src/merge.ts`）

`markers.ts` 早就能写出/读懂标记，缺的是「拿到三份内容之后怎么合」。

| 区块 | 规则 |
|---|---|
| `todo` / `handwritten` | 一律保留磁盘内容。todo 就是「等人来填」的容器，填完就该留住 |
| `generated` | 磁盘内容哈希 == manifest 基线 → 换成新内容；不等 → 报冲突、保留磁盘 |
| 磁盘多出的区块 | 报冲突。不猜该挪到哪，挪错位置的代码比丢代码更难查 |
| 磁盘完全没有标记 | 不合并（`unmergeable`）。用户可能整体重写过，此时自动合并就是猜 |

三个设计判断：

- **按区块合，不按行做 diff3。** 生成代码的区块内部是整块重写的（一个 columns 数组、
  一个方法体），行级 diff3 会把一次改名劈成几十个碎冲突，用户得逐个点。
- **区块外以生成为准。** 手写内容要放进 `@dsg:handwritten` 区块（文件头那句提示就是
  这个意思）。反过来「区块外也做 diff」会让每次契约改动都变成冲突，用户只能天天
  `--force`，合并等于不存在。
- **manifest 基线记纯净生成内容，不记合并结果。** 这是最容易写错的一处：若把合并后
  的磁盘内容记成基线，下一次生成会认为「没人改过」，直接覆盖——todo 区块里的实现
  当场丢失。

实测踩到的反例：最初合并时顺手把标记行的 `hash=` 刷新成磁盘内容的哈希。结果「只改了
区块内容」的文件在合并后与磁盘不再逐字节相同，`gen --check` 把它报成漂移，CI 从此
每次红灯而用户什么都没改。改为**磁盘侧标记行原样保留**（哈希只归 manifest 管，文件里
那份是给人看的快照）。

### 2. 生成器开始写区块

| 位置 | 区块 | 理由 |
|---|---|---|
| NestJS `*.service.ts` 每个方法体 | `todo`，名字 = operationId | 业务逻辑全在这里，是最怕被覆盖的地方 |
| NestJS `main.ts` 鉴权挂载点 | `todo name=auth` | 几乎每个项目都要改，而 main.ts 会随 Swagger 开关重新生成 |
| Vue 页面 `<script setup>` 末尾 | `todo name=custom` | 埋点、权限判断、跨页联动在 IR 里没有词汇 |

### 3. `gen` 与 `--check` 共用同一套规则

- `gen`：手改文件先尝试合并 → `merged` 写合并结果、`conflict` 保留磁盘并列出
  「哪个文件哪个区块为什么」，退出码 1；`--force` 仍然覆盖。
- `gen --check`：期望内容也走一遍合并。**往 todo 区块里写代码不算漂移**，
  否则任何实现了业务逻辑的项目都会被 CI 卡死；只有区块外对不上才报漂移。
  判定只认 `merged`/`unchanged`，`conflict`/`unmergeable` 一律算漂移。

### 4. CI workflow（原来完全没有）

新增 `.github/workflows/ci.yml`，步骤与 `pnpm verify` 一一对应：install → build →
typecheck → typecheck:tests → test → smoke。本地跑什么 CI 就跑什么，避免「本地绿、CI 红」
之后大家开始改 CI 而不是改代码。

顺带修了两处被 CI 暴露出来的旧问题：

- `vue-generator.test.ts` 把 `rowKey` 直接挂在 IR 的表格组件上——IR 里这个字段叫
  `rowKeyFieldRef`（UI Schema 才叫 `rowKey`）。运行时因为是 JS 对象所以没报错，
  但类型检查一跑就红。
- 单测默认 5s 超时对 `gen` 的端到端用例太紧（并发 25 个 worker 时单条 4–6s），
  已把全局超时提到 20s。

### 5. 顺手清掉一处过期提示

`apps/web` 的组件检查器里有一句「这个容器类型 Vue 生成器还没实现（P1 TODO）」，
而 tabs/card 在 `0134437` 就实现了。这种提示比没有提示更糟——它会让用户主动避开
一个本来能用的功能。已连同样式一起删除。

### 6. 现在的状态

测试从 701 增至 730（新增合并单测 12 条、CLI 往返 3 条），`pnpm verify` 全绿。

`x-dsg-mappings`、`dictionaries.models`（死数据）、`sample` 的 `pattern` 反向造数
这类零碎项仍在，但都不影响主链路。
